# kead

Personal operating-system app. **Next.js 15 (App Router) + React 19 + Tailwind v4**, backed by Supabase (Postgres + auth). Deployed to [kaed.hu](https://kaed.hu) from Vercel — auto-deploy on every push to `main`. Dev server runs on **port 4321** (`npm run dev`).

> Earlier versions of this file described an Astro stack. That is gone — there is no `Layout.astro`, no `astro:transitions`, no scoped `<style>`. Anything below is Next.js.

## Architecture

- `app/` — pages are **Server Components** (`async function Page()`); mutations are **Route Handlers** under `app/api/**/route.ts`.
- `lib/` — framework-agnostic data access, types, and per-feature business logic. `lib/auth.ts` and `lib/supabase.ts` are the auth/DB entry points.
- `components/` — shared client UI: `ui.tsx` (the design system as Tailwind class strings), `InlineEdit.tsx`, `Popup.tsx`, `Nav.tsx`.
- `middleware.ts` — refreshes the Supabase session cookie on every request (Server Components can't write cookies, so without this an expired token is never renewed).
- `supabase/schema.sql` — source of truth for the database, **not** auto-applied (see below).

## Auth

- `requireUser()` / `requireOwner()` (in `lib/auth.ts`) resolve the signed-in user for a **page** and `redirect('/login')` (or `/finance` for the restricted `member` role) when there's no session. They throw Next's redirect, so callers get a plain `Session` back — no union to narrow.
- `getSession()` / `getOwnerSession()` are the **Route Handler** variants: they return `null` instead of redirecting, so the handler can answer with a JSON 401.
- `isMember(user)` — the `member` role is scoped to the finance tracker only. Owner-only pages call `requireOwner`; owner-only routes call `getOwnerSession`; owner-only inline-edit fields pass `ownerOnly: true` to `createFieldRoute`.

## Patterns to follow

- **Never `await` independent Supabase queries one at a time in a Server Component.** Use `Promise.all([...])` when the queries don't depend on each other — sequential awaits were the single biggest "the app feels slow" cause, paying 3–4× round-trip latency per page.
- **Two mutation styles, used deliberately:**
  1. **Plain `<form method="post" action="/api/…">` + 303 redirect.** The default. The Route Handler reads `request.formData()`, writes, and `NextResponse.redirect(new URL(path, request.url), { status: 303 })` — usually back to the same page with `?error=…` on failure, which the page renders via `<FormError>`. A plain `<form method="post">` is a real browser navigation, so the page **does reload** (it is not a Next soft navigation). Use this for rare creates/updates and for no-JS fallback; anything used repeatedly should use style 2 instead.
  2. **Client component + `fetch` returning JSON.** For interactions that must update without a page reload. A route serves both styles by checking `Accept: application/json` (JSON `{ ok, … }` vs the 303 redirect), so the form keeps working without JS: Painhunter's `QuickAddPain`, `NewPainPopup` and `PromoteButton` post through `app/painhunter/submit.ts#postForm`, then `startTransition(() => router.refresh())` (or `router.push` for a destination) with the button disabled and relabelled while it runs. `InlineEdit` (click-to-edit cells) POSTs `{ field, value }` and calls `router.refresh()` on success. The business-ideas card list (`app/business-ideas/IdeaList.tsx`) goes further — it holds the ordered list in local state and applies **optimistic** delete/reorder, rolling back and showing the error on failure, with no `router.refresh()` at all.
- **List rows delete/archive without a refresh via `components/CardList.tsx`.** Wrap a grid/table in `<CardList>` (`as="tbody"` for tables), each row in `<CardItem id=…>`, and put a `<RemoveButton id=… endpoint=…>` where the delete `<form>` was. A successful POST hides that row instantly; the server drops it for good on its next render. Used across projects, goals, opl, specific-knowledge, studies, system-design, idea-lab, and the finance tables. Reorder still needs bespoke local state (`IdeaList`, `GoalGrid`).
- **A card shows only its title row; everything else is behind `CardDetails` (`components/CardDetails.tsx`).** The head row (title plus its icon actions: open, archive/restore, delete, drag/rank) is all that's visible; every status/category pill, chip, score, date, link and long field goes inside one `<CardDetails preview={…}>`: a native `<details>`, **closed by default and opened only by clicking its summary**, with a one-line glimpse of the first field next to the label. The content stays mounted while closed, so `InlineEdit` inside works unchanged. Applies to business ideas, OPL, projects, goals, specific knowledge, studies, the system-design cards, Painhunter's mobile cards, and the three archive pages (where Restore is a ↺ icon beside the ×, not a footer button). Exceptions: think-pad cards (title + date only), and the CMS site, system-design project and bank cards, which are whole-card links or dashboards. Don't add an `open` default or auto-open it from code.
- **Inline-edit endpoints share one implementation: `createFieldRoute` (`lib/field-route.ts`).** A feature's `app/api/<feature>/[id]/field/route.ts` is just a table name + a `fields` spec (`text` / `enum` / `int` / `number` / `ref`, each with its own validation + error message). Use `onWrite` for cross-column rules and `afterWrite` for side effects that need their own row (history logging) — `afterWrite` errors are swallowed because the edit itself already saved.
- **One-shot mutation endpoints (delete/archive/restore) share `createMutationRoute` (`lib/mutation-route.ts`)** — most are one line: `export const POST = deleteRow('projects', '/projects')`. It content-negotiates: JSON for `Accept: application/json` (the `RemoveButton` path), a 303 redirect (`?error=…` on failure) for a plain `<form>` — so the same route backs both the async list control and the plain forms still on detail pages. Pass `ownerOnly` to match the table's access rule; a `run` can return `{ redirectTo }` to override the form landing per-request (see the system-design routes, which look up `project_id`).
- **All styling is Tailwind utilities composed from `components/ui.tsx`.** `app/globals.css` is tokens only (`@theme` block) — no component classes. There is deliberately no hand-written CSS and no specificity to reason about; the Astro rewrite existed to kill 1384 lines of colliding CSS. Add a new visual primitive as an exported class string in `ui.tsx`, not a `.css` rule.
- **Client components own their own event listeners** (React) — there's no document-delegation requirement here. `'use client'` only where interaction actually needs it; keep pages as Server Components.

## Finance module

- `finance_limits` is a single shared row: `daily_limit`, `weekly_limit` (optional overrides), and `starting_savings_balance` (added on top of the sum of `saving`-type transactions everywhere a savings balance is computed — see `/finance` and `/finance/budget`).
- `finance_categories.default_amount` is the category's default planned monthly amount. `/finance/budget`'s `budgetedFor(cat)` helper falls back to it whenever no month-specific `finance_budgets` row exists yet — a fresh month shows the default plan pre-filled and editable, only persisted once Save is hit for that category+month. Use that helper everywhere a "planned amount for this category this month" is needed; don't recompute the fallback inline.
- `finance_categories.interest_rate` (nullable, percent per month, e.g. `0.5`) is only meaningful for `type = 'saving'`. `/finance/budget`'s forecast panel computes a contribution-weighted blended monthly rate across saving categories and compounds it (future-value-of-ordinary-annuity formula) instead of flat linear growth — see the `projections` block.
- `/finance/settings` is the **only** place categories are managed (add/delete/edit name, default amount, interest rate via inline `[data-editable]` cells) — there is no separate "Manage categories" popup on `/finance`; don't re-add one.
- `/finance` has a quick-add bar (category + amount, posts to `/api/finance/transactions/create`, dated today) for fast logging without opening the full "+ Add transaction" popup.
- A "Statistics" nav entry on `/finance` is a disabled placeholder ("Soon" badge) — intentionally not built yet, on hold per the user.
- Daily/weekly spending limits on `/finance` derive from the current month's planned expense budget by default (`/finance/budget`), overridden by `finance_limits` if set.

### Investments (`/finance/investments`)

- Owner-only: the page uses `requireOwner`, and the link on `/finance` renders behind `!isMember(auth.user)` — the shared `member` role can reach `/finance` but never this.
- Prices come from CoinMarketCap server-side. `CMC_API_KEY` is read via `process.env` and is **not** `NEXT_PUBLIC_` — keep it server-only so it never reaches the client bundle.
- The free CMC plan allows **one `convert` option per call**, so `convert=HUF,USD` is rejected. Quotes are fetched in USD and the forint rate comes from one `/v2/tools/price-conversion` call; every HUF figure is `usdPrice * rate`, so the displayed rate always matches the rate used.
- Symbol and slug lookups **cannot be mixed in one call**. Symbols are batched into a single request; each slug costs its own. Results cache 5 minutes per server instance so a refresh doesn't burn credits — `?refresh=1` forces a fetch.
- `positionMetrics()` in `lib/investments.ts` owns every derived column (value, change, %, goal value, upside). It returns `null` rather than `Infinity`/`NaN` for a zero cost basis, missing quote, or zero price — don't recompute these inline.

## Supabase schema changes

- `supabase/schema.sql` is the source of truth but isn't auto-applied — there's no linked Supabase CLI project (no DB password on file).
- To run a migration: use the Management API directly with the token in `.env` (`SUPABASE_ACCESS_TOKEN`):
  ```bash
  TOKEN=$(grep SUPABASE_ACCESS_TOKEN .env | cut -d= -f2)
  curl -s -X POST "https://api.supabase.com/v1/projects/jugffqdvvjvusaxowhim/database/query" \
    -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
    -d '{"query":"<sql>"}'
  ```
  This is a real, irreversible action against production — always confirm with the user before running DDL this way, then update `supabase/schema.sql` to match.

## Remote MCP endpoint

- `app/api/mcp/route.ts` exposes the same Supabase table access as the local `mcp-server/` stdio server, over HTTP, for claude.ai connectors (e.g. mobile). `export const dynamic = 'force-dynamic'`.
- Auth: bearer token via `MCP_AUTH_TOKEN` (Vercel env var), checked from either the `Authorization` header or a `?token=` query param — the query-param fallback exists because claude.ai's custom-connector UI (without OAuth) doesn't send a custom header.
- Access uses the **service-role key** (`SUPABASE_SERVICE_ROLE_KEY`), which bypasses RLS, so operations are restricted to a known `TABLES` allowlist in the route rather than arbitrary table access.
- Known weakness: static token, full read/write/delete, token visible in logs/history when passed as a query param. If this ever needs to be more than "good enough for personal use," the fix is proper OAuth (dynamic client registration), not a static bearer token — not yet built.
- Beyond the generic `select_rows`/`insert_row`/`update_rows`/`delete_rows` tools, dedicated tools exist for interactions that shouldn't require the chat session to know the schema (the CMS tools and the Work tools, below). Keep `mcp-server/index.js` (the local stdio server) in sync with any tool or `TABLES` change here — they're meant to mirror each other.

## Think Pad (`/think-pad`) — the business-starter playbook

A self-assessment and execution planner: the YC Startup Library boiled down to 13 phases (0–12) and ~115 steps, worked through once for you and once per business idea. It replaced the old wiki on 2026-10-24 (the `think_pad_pages` / `think_pad_entries` tables are still in the database, empty and unused; the wiki UI, `lib/think-pad*.ts` and the `save_thought` MCP tool are gone). Meant to be automated later, so the answers are structured and in the MCP allowlists.

- **The steps live in code, the database holds only answers.** `lib/playbook.ts` (`PHASES`, `ALL_STEPS`, `ANCHORS`, `CANVAS`) defines every phase and step; editing wording or adding a step needs no migration. Step numbers are global — "#27" means the same thing in every run — and step 201 is the gate after validation (`GATE_VALIDATED`).
- **Two kinds of run, by `scope`.** `you` steps (phases 0–2: mindset, personal setup, finding problems) are answered once; `idea` steps (everything from #24/#25 and phase 3 on) are answered per business idea. Tables: `playbook_runs` (one per idea, plus one with `idea_id` null for You — partial unique indexes) and `playbook_answers` (PK `run_id, step`; `status`, `note`, `data` jsonb). A run row is created lazily on the first write. The idea picker lists active `business_ideas`; the URL is `/think-pad?idea=<id>`.
- **Statuses.** `todo` → `doing` → `done` (click cycles), `skip` (from the open row). Decision steps (#201 gate, #52, #85) answer `go` / `pivot` / `kill` instead. "Finished" for progress (`isFinished`) is anything but todo/doing. New status values need the `playbook_answers.status` check constraint changed.
- **Connections between steps.** A step with an `anchor` stores a key answer (target customer #27, the problem #34, why me #39, pitch #40, outcome #41, price #42, where they are #62, main metric #79, …). Those answers fill the **canvas** at the top of the page and are quoted under every step that lists them in `uses`; a step whose anchor is still empty shows a red "needs …" chip that jumps there. Idea steps can also build on You-run anchors (advantages #10, people I know #11); those chips link to `/think-pad#step-N`, and `Playbook` scrolls to the hash on load. Step #24 is the one structured step: four 1–10 scores in `data` (`SCORE_AXES`), average shown, auto-`done` when all four are set.
- **UI.** `page.tsx` (server) loads ideas, runs and answers and passes one run's answers (plus You's, for quoting) to `Playbook.tsx` (client): progress bar and phase rail, canvas, then the phases as an accordion (the first phase with an unfinished step opens). Saves are optimistic `POST /api/playbook/step` calls — `{ idea_id, step, status? | note? | data? }`, only the sent fields are written, the response is always JSON — rolled back with an inline error if they fail. Notes save on blur, not per keystroke. No page reload anywhere.
- **MCP.** `playbook_runs` and `playbook_answers` are in both `TABLES` allowlists, so a chat or a later automation can read the answers and write notes/statuses (find or insert the run row first: one per idea, `idea_id` null for You).

## Work (`/work`) — the Knorr-Bremse day-to-day ticket list

The "Work" menu group (first in the nav). One page: the user's Jira-style tickets as an **open point list in an Excel-like grid**, with a description, a comment history and a time log per ticket, all scriptable by Claude. It is a list the user fills (and pastes into from Jira or Excel), **not a live Jira sync** — that would need the company's Jira URL and a token. A Jira key can be stored on a row so a later paste or an automation lines up with it.

- **Tables** (`supabase/schema.sql`): `work_tasks` (`no` identity = the OPL "No." column, optional `jira_key` unique per user, `title`, `description`, `responsible`, `status` todo/doing/blocked/done, `priority` high/medium/low, `due_on`, `done_at`), `work_comments` (dated history, never edited; `source` app/claude/import) and `work_logs` (hours per ticket per day, `numeric(5,2)`, ≤ 24; same `source`). The view `work_task_stats` (security_invoker) gives each ticket its comment count, latest comment and total hours, so nothing fetches every comment (PostgREST caps responses at 1000 rows); `withStats` (`lib/work-server.ts`) joins it in.
- **Rules live in `lib/work.ts`** (`cleanTask` validates any subset of the writable fields and settles `done_at` from `status`; `parseHours` accepts `1.5`, `90m`, `1h30`, `1:30`; `todayInBudapest`, `weekStart`). The routes, the grid and the MCP tools all call it, so they can't disagree. `lib/work-import.ts` (`parseTasks`) reads tab-separated text from Jira/Excel or CSV, with or without a header row; it maps Jira's column names, statuses (`On Hold` → blocked, `In Review` → in progress), priorities (`Highest`/`Blocker` → high) and dates (`28/Oct/26`, `28.10.2026`).
- **The grid** (`TaskGrid.tsx`, client): gridlines, frozen header, active cell moved with the arrow keys, Enter/F2 or just typing to edit, Tab/Enter to commit and move on, Esc to cancel, Delete clears; click a header to sort; the last row is a "+ Add a row" input (typing `KB-123 Summary` splits the key out). Status and priority are always-visible dropdown cells. "Latest comment" and "Logged" are read-only roll-ups; the ▸ in the No. column opens `TaskDetail` (description saved on blur, comment box, time-log form). Saves are optimistic `POST /api/work/tasks/[id]` calls (only the sent fields), rolled back with an inline error on failure; no page reload. "Copy table" puts the visible rows on the clipboard as TSV for Excel; "Paste from Jira / Excel" (`ImportPopup`) previews, then `POST /api/work/tasks/import` (a Jira key already on the list updates that row; a pasted comment becomes the first comment of a new row).
- **Automation with Claude.** `lib/work-mcp.ts` adds `work_list_tasks`, `work_get_task`, `work_create_task`, `work_update_task`, `work_add_comment`, `work_log_time` and `work_daily_update` to the remote MCP endpoint (the stdio server only gets raw table access to `work_*`). A ticket is addressed by Jira key or row number. `work_daily_update` applies a whole day's notes — typically parsed by Claude from a plain text file — in one call and is idempotent: an identical `claude` comment (±18 h) or identical time entry (ticket, day, hours, note) is skipped, so a scheduled run can't double-log. The page's closed-by-default "Automate with Claude" guide shows the text-file format and the prompt.
- **Not built (ask before adding):** a real Jira sync, editing a comment (they are append-only), attachments, a link from the Jira key to the Jira site (needs the base URL).

## Painhunter (`/painhunter`) — the pain log that feeds the business idea register

Upstream of `/business-ideas`: every problem noticed (slow, manual, annoying, expensive, done in Excel) is one **line in a table** (not a card grid), scored, and linked to the ideas it supports. Otherwise the business-ideas conventions — `InlineEdit` fields, `CardList`/`CardItem` + `RemoveButton` archive and delete, an `/archive` page — but **no manual rank**.

- **Tables:** `pain_points` (title, `details`, `who`, `workaround`, `source`, `context`, `noticed_on`, five `score_*` smallints, `archived_at`) and `pain_point_ideas` (many-to-many join to `business_ideas`, composite PK, cascades both ways). Archiving a pain keeps its links.
- **Scores are three worded levels, stored as 1–3.** Each of Pain / Frequency / Money / Access / Fit has its own low→high words in `SCORES[].levels` (`lib/painhunter.ts`): Pain Mild·Annoying·Severe, Frequency Yearly·Weekly·Daily, Money Little·Some·Lots, Access Hard·Possible·Easy, Fit Low·Good·Perfect. `SCORE_LEVELS` (3) drives the field route's allowed values and `SCORE_MAX` (15). The DB check constraint still says `between 1 and 5` — it was never tightened, so no DDL was needed; only 1–3 is ever written.
- **Order is the score.** `painScore()` (`lib/painhunter.ts`) is the sum of the five levels and is `null` until all five are set, so a half-scored pain never outranks a fully scored one. `compareByScore` puts fully scored first (highest total), then the rest newest-first. The top three fully scored lines get a ★ under their total — only in the unfiltered, score-sorted view. Don't recompute the total inline.
- **`source`** is which of the seven discovery methods found it (journal, would-buy, interview, existing spend, why now, boring industry, funded gap) — a DB check constraint, so adding a value means changing the constraint *and* `PAIN_SOURCE_LABELS` / `PAIN_SOURCE_OPTION_LABELS` and the `PILL` map in `components/ui.tsx`. **`context`** (where it happens) is **free text**, not an enum: the quick-add bar and popup use a plain text input, the card edits it inline, and the context filter chips are built from whatever is in use, grouped case-insensitively (`contextGroups` / `contextKey`; the URL carries the lowercase key).
- **The guide** at the **bottom** of `/painhunter` (`PainhunterGuide`, a native `<details>`, **closed by default**) is the "where to look" note: the seven methods, what to avoid, how to filter, the first two weeks. Its wording is verbatim from the source note and lives in `lib/painhunter-guide.ts` — edit text there. The seven methods map one-to-one onto the `source` values, so each shows how many pains were logged that way and links to that filter.
- **Desktop table, mobile cards:** `PainTable` (server) renders both views inside one `<CardList>`, CSS picks one at the `lg` breakpoint, and a remove in either hides the pain in both. Wide screens get one line per pain — `PainRow` (client), its own `<tbody>` via `<CardItem as="tbody">`: chevron, total, title (with the source pill and context chip under it, to leave the worded score columns room), the five scores, an idea count, archive/delete; the chevron opens a detail line. Below `lg`, `PainMobileCard` shows only the title (and archive/delete); the total, source, context, the five scores (3 per row) and the rest are behind its `CardDetails`. Both share `PainDetails` (what happens / who has it / how it is handled today / date / idea links / promote), so they always offer the same edits. The scores are five always-visible dropdowns showing the level words (`ScoreSelect`) that save on change and `router.refresh()` so the total and the ranking catch up — a fully scored line jumps to its ranked place. `/painhunter/archive` follows the same table/cards split.
- **Everything on `/painhunter` saves without a page reload.** Quick-add (`QuickAddPain`, clears and refocuses for back-to-back entries), the "Log a pain" popup (`NewPainPopup`, closes on success), "Make it a business idea" (`PromoteButton`, `router.push`es to the new idea), scores, inline edits, linking and archive/delete all `fetch` and refresh the server render in place; `/api/painhunter/create` and `/[id]/promote` answer JSON to `Accept: application/json` and still redirect for a plain form.
- **Frustration journal:** the quick-add bar at the top of `/painhunter` posts a `source=journal` row dated today in Europe/Budapest (`todayInBudapest`); the "Journal n/30 days" chip counts distinct journal days in the last 30 (`journalDays`).
- **Filters and sort are plain `?source=&context=&idea=&sort=` URLs** (no client state) in one compact toolbar row: `FilterSelect` dropdowns for source and context (options are the filtered hrefs, so the row stays one line however many contexts exist), a `Clear` link, the stats text, and a `segmented` Best score / Newest toggle; `?idea=<id>` is what the "N pains" chip on a business idea card links to.
- **Linking:** `IdeaLinks` (client) POSTs to `/api/painhunter/[id]/link|unlink` then `router.refresh()`; link is `ON CONFLICT DO NOTHING`. "→ Make it a business idea" (`/api/painhunter/[id]/promote`) creates the idea from the pain (title, `pain_point`, `target_market` ← `who`), links it, and opens the new idea; it only shows while a pain has no linked idea. Business idea cards show the linked-pain count (active pains only, so it matches the filtered view) and the idea page lists them.
- Score edits go through `createFieldRoute`'s `enum` kind (`'1'`–`'3'`), with `onWrite` converting to a number for the smallint column.
- Both tables are in the MCP `TABLES` allowlists (remote route and stdio server).

## Blog CMS (`/cms`) — the posting machine for the client sites

Sales & Marketing → Blog CMS. One `cms_sites` row per site (kazanszerelok, temptech, jobro, klimaepito), each with an ideas queue, posts, a brand brief, a posting schedule and a Vercel deploy hook.

- **Flow:** you (or an MCP chat) add ideas → `lib/cms-run.ts#runSite` turns the oldest queued idea into an SEO article via Claude (`lib/cms-generate.ts`, tool-use for structured output; model `claude-sonnet-5-5`; `tool_choice` forcing is NOT supported on it, so the prompt tells it to call `save_post`) → the post is `scheduled` at the next slot (`nextSlot`, DST-safe via Intl) when the site is in **auto-publish** mode, or left as a `draft` in **review** mode (the default) → when due it goes `published` and the site's deploy hook fires so the static site rebuilds.
- **Heartbeat:** `/api/cms/cron` (vercel.json, daily 05:00 UTC, `?lookahead=23` because Hobby crons can't hit an exact hour — everything due within 23h goes live). Auth: `Authorization: Bearer $CRON_SECRET` (Vercel adds it) or the signed-in owner. Any external scheduler can call it hourly without `lookahead`. Generation takes ~1 min, so `maxDuration = 300` and at most one article per site per pass ("Write next post now" on the site page forces one).
- **Public read API for the sites' builds:** `GET /api/cms/v1/posts` and `/posts/[slug]` with `Authorization: Bearer kck_…`. Keys are per site, only the sha256 is stored, the plaintext is shown once on the site page (Regenerate to rotate). Served with the service-role client after the key check; only `publicPost()`'s fields leave.
- **Body is Markdown** (`body_md`, `##` headings, no H1). Consumers render it themselves (kazanszerelok uses `marked`). Cover pictures: upload to the public `cms-media` storage bucket (`/api/cms/media`) or paste a URL.
- **MCP:** `lib/cms-mcp.ts` adds `cms_list_sites`, `cms_add_ideas`, `cms_list_posts`, `cms_get_post`, `cms_create_post`, `cms_set_post_status`, `cms_write_next_post`, `cms_rebuild_site` to the remote endpoint. The stdio server only gets raw table access to `cms_*` (it can't import `lib/`).
- **Connecting a site:** on the site's page create an API key and paste its deploy hook; in the site's own project set `CMS_API_URL=https://www.kaed.hu` and `CMS_API_KEY`, and fetch at build time (see kazanszerelok's `src/lib/cmsClient.ts` + `getBlogPosts.ts`, and its sitemap `serialize` for `lastmod`).
